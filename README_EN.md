### 🎨 Vibe Coding in Practice: EasyLife

A**flagship project from Sep–Oct 2026** and my representative vibe-coding case: **the entire chain from PRD to a real device was AI-driven, with most of my effort deliberately spent on UI and motion design.**

**Why this project as the vehicle**

The biggest risk in vibe coding is "it works, but it doesn't look good" — AI-generated UI is often functionally correct yet completely lacking in polish. I intentionally picked calorie tracking as the subject because its core problem is **abstract feedback** (you only know you ate 300 kcal more, not what that means). That forced me to spend my effort on interface feedback and motion rather than piling up business features.

**Where the UI / motion effort actually went**

| Area | Approach |
|------|----------|
| **Water bottle liquid** (the home-screen core) | Not an image — a **Canvas 2D real-time physics simulation**: dual-mode forced damped oscillators (M1: cos(πu), T=460ms, ζ=0.14; M2: sin(4πu+φ), 0.955 decay, normalized dt), 34-segment surface path + 8 bubble pool + 12 particle pool. Tapping the bottle injects a disturbance; it wobbles twice, then settles. **No wobble on first entry** — a calm opening |
| **Theme system** | Three themes (Mint / Ocean / Lavender) × light/dark = a **6-slot token matrix, 20 role tokens**. Key decision: **abandoned CSS variables** for per-element inline `:style` binding — uni-app x's native side has no reliable cascade or CSS-variable channel |
| **Visual assets** | All 347 food icons **AI-generated**, with the original PNGs archived into the repo (image generation isn't reproducible — no archive means no recovery). Visual direction: the mint-droplet style |
| **Restraint in over-budget feedback** | Three color levels (green / amber `#E8B54D` / coral `#FF9E7D`) — **never red when over budget**: red is an error color; coral warns without discouraging |
| **Real-device visual tuning** | A 15px label looks fine in the design file and tiny on a real device. Only rpx + px tuning page by page converged it — an iteration loop that only a real device can expose |
| **Device capability tiers** | high / mid / low tiers detected from model/chip; low tier auto-disables haptic feedback, liquid ripples and frosted glass |

**Scale**: 8 routes / 9 components / 6 Pinia stores / 347-item food library / ~12k lines of `.uvue` + `.ts`, local-only storage with no server, running independently on Android / WeChat mini-program / Web H5.

**The vibe-coding workflow and its trade-offs**

```
① PRD → ② DesignTokens (single source of truth for color/type/radius) → ③ clickable HTML prototype
→ ④ AI-generated hi-fi visual designs → ⑤ implementation → ⑥ real-device acceptance → ⑦ per-page rpx/px visual tuning
```

- **Design first**: `design/DesignTokens.md` is the single source of truth for colors, type scale and radii — every color in code must map back to it, which stops pages from slowly drifting into two design systems.
- **Docs as context**: five ADRs in `docs/decisions/` plus a uni-app x pitfall log — because the native side has a class of bugs that "work on the web but fail silently in native," and those are worth remembering.
- **Where AI stops**: AI can quickly produce a usable interface, but **finish and polish cannot be delegated** — real-device acceptance and page-by-page visual tuning are entirely manual.
